# Feature parity with NANSEN dev

This page lists what NANSEN's `dev` branch does and where the rebuild does the same: in Python, in MATLAB, in the dashboard, and which tests exercise it. It covers 286 features of dev, taken from its source:

- the main app (`apps/+nansen/@App/App.m`): its menus, the session table's context menu, the run modes and their keys, the table viewer, the file viewer, the task processor and the preferences;
- the session methods of the core and two-photon modules, and the toolbox wrappers;
- the apps imviewer, roimanager, roiclassifier, signalviewer and fovmanager, with their plugins, menus and key bindings;
- data variables, file adapters, the image stack and ROI formats, the data cache;
- data locations, pipelines, notes, modules and add-ons;
- what the legacy importer carries over from a dev project.

Menu items that dev disables or comments out (Watch Folders, Manage Metatables, Manage Variables, New Data Variable, Reactivate All Popup Tips, imviewer's Save Stack, Export Stack and Export Image As, roimanager's Show Text Labels and Edit Settings, the multipart figure menu) are left out.

## How it was checked

Every pointer in the matrix was checked by a script before this page was written, not typed from memory:

- a code pointer is `file` and a name, and the file must contain that name (`api.py` `entities__list` is the Python handler of `entities.list`, `Api.m` `apiEntitiesList` the MATLAB one);
- a dev pointer is a file under dev's `code/` folder, and the menu text, tag or function named must be in it;
- a test must exist, and where a name follows it (a selector, a key, a method), that name must be in the test's body;
- a conformance pointer is resolved to the request ids of the steps that call that method (with that `methodId`, projection or option) in `conformance/api/<case>/session.json`, or names a case of another kind (`conformance/<kind>/<case>`, and the key of its `expected.json` the row relies on).

Test notation: py `name` is in `python/tests`, m `Class/method` in `matlab/tests` (`ExternalToolsTest` in `matlab/externaltests`, run against the real toolboxes), ui `name` is a Playwright test in `python/tests/test_ui.py`, conf `case` method #ids are conformance steps, run by both languages. dev's paths are relative to its `code/` folder. The rebuild's are relative to the repository, shortened: Python's core files are in `python/src/nansen/`, dashboard files in `ui/js/`, and `ophys/` and `core/` are `modules/ophys/` and `modules/core/`.

## Status

- **Both languages**: the feature works from the MATLAB app and from the Python app. Dashboard-only features (sorting a column, the colormap) count here, since one dashboard serves both.
- **Improved**: carried over, in both languages, but done differently from dev, and better: it does strictly more, is safer, faster, or works in both languages where dev's did not; the row says how.
- **Equivalent**: carried over, in both languages, but done differently from dev, with the same capability (another interface or mechanism); the row says how.
- **MATLAB only** / **Python only**: carried over in one language; the row says why.
- **Not carried**: not in the rebuild; the row says why.

The Improved and Equivalent rows have an **Assessment**: why the rebuild's way is an improvement or equivalent, judged against what dev's code does. Thirteen of them were weaker than dev, something a dev user could do and then could not, or less well, and were made good in both languages, the dashboard and the tests; they say *weaker → fixed* and what was added. Three differ in a way inherent in the languages (the NoRMCorre and flufinder toolboxes and dev's imviewer are MATLAB code), and say so.

No dev feature is carried over to Python alone. The four MATLAB-only rows are dev's own MATLAB code (a dev project's MetaTables, session methods and file adapters, and the EXTRACT toolbox); Python lists, queues and converts all of them and hands the run to a MATLAB worker.

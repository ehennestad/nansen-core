# Modules, methods and tasks

A **module** is a folder that adds fragments, methods, file adapters and pipelines to the projects that list it. A module holds code for either language or both, and the same module can be used from MATLAB and from Python.

## A module folder

```
<module>/
  module.nansen.json                 nansen.module: id, version, and the paths of what it provides
  fragments/<name>.fragment.nansen.json
  methods/<name>.method.nansen.json
  adapters/<name>.fileAdapter.nansen.json
  pipelines/<name>.pipeline.nansen.json
  presets/<name>.options.nansen.json    option presets of its methods (or of other modules' methods)
  dashboard/<name>.js                pages it adds to the dashboard
  python/                            Python code, imported from here without changing sys.path
  matlab/                            MATLAB code, put on the path when one of the module's methods or adapters is first used
```

`module.nansen.json` lists each document by its path in the folder. Nothing is found by scanning. Ids of everything a module provides start with the module id, for example `core.notes` or `ophys.motion_correction`.

A project lists its modules in `project.nansen.json` (`modules: [{id, path?}]`). Add one with `project.addModule(id, path)` (MATLAB) or `project.add_module(id, path)` (Python). A module is looked for in this order: at `path` (relative to the project folder), at `<project>/modules/<id>`, and among the modules that ship with NANSEN (`modules/` in this repository). The project's own `fragments/`, `methods/` and `pipelines/` folders work like a module without an id prefix.

The built-in **`core`** module provides:

- `core.notes`: `ignore` and `description` for any entity;
- `core.subject`: date of birth, sex (a choice) and species, for subjects;
- `core.pipeline`: the pipeline an entity is assigned;
- `core.file_stats`: file count and size, computed by `core.file_stats`;
- the methods `core.export_keys` (batch), `core.backup` (copies an entity's folders to `<destination>/<data location>/<the same path>`, leaving copies that are up to date alone) and `core.wait` (for trying the queue);
- the pipeline `core.inspect`.

## The ophys module

The built-in **`ophys`** module brings over the core of dev's two-photon workflow (`+nansen/+module/+ophys/+twophoton`). Its methods are native in both languages and give the same results, which the `ophys` conformance case checks on a synthetic recording with known shifts and cells. Stacks are height x width x frames in both languages (`stack[y, x, t]` in Python is `stack(y+1, x+1, t+1)` in MATLAB, and `.npy` files keep that indexing). Python needs NumPy and, for TIFF, tifffile: `pip install "nansen-core[ophys]"`.

Its `tutorial/` folder describes the two-photon quickstart (`demo.create` with `kind` `two-photon`; see [getting started](../getting-started.md)): `tutorial.json` sets the synthetic recordings and the project, and `dataset.dsm.json` is the project's DSM config.

Variables that exist are left alone |
| `ophys.read_metadata` | The frame rate, pixel size and z step the recording's files give (the metadata of its stack, `stack`, by default `TwoPhotonSeries_Original`), written into the entity's `frame_rate` (`ophys.imaging`), `pixel_size_um` (the pixel's width) and `z_step_um` (`ophys.scan`) columns, those its table has; a value the files do not give is left as it is. `data.traces` then has the frame rate for its seconds axis. A preview writes nothing |
| `ophys.motion_correction` | Motion correction: each frame is aligned to a reference by the shift of largest phase correlation (smoothed as suite2p does), within `maxShift`. Rigid and in whole pixels by default. `subpixel` finds shifts to 1/20 pixel, by computing the correlation on a finer grid around its peak (as NoRMCorre does), and moves frames bilinearly. `patches` above 1 corrects piecewise rigidly (as NoRMCorre): the frame is cut into patches x patches patches, each finds its shift within `maxDeviation` of the frame's, and each pixel moves by the shift interpolated between the patch centres. Both weight frames by a Hann taper first, so the frame's edges do not count. Before alignment, `numFlybackLines` rows are left out at the top of each frame, and `bidirectionalCorrection` moves the lines a resonant scanner scans back (every other row) by their column offset from the lines scanned forth, found once in the first frames (`constant`) or in each chunk (`continuous`, as dev's); `stretchCorrection` `sciscan` undoes a resonant scanner's stretch of the lines (its mirror's sinusoidal speed) by dev's profiles of the SciScan rig (`calibration/sciscan_stretch.json`, from dev's destretch lookup table: the displacement of each column, measured on a microgrid, for each zoom and line width): raw column c lands at c − displacement(c), the corrected line is read at the whole places from the first column's to the last's by linear interpolation (dev used cubic), so the stack is a little narrower; the zoom is `zoomFactor`, or the recording's (SciScan's `ZOOM`), and the nearest zoom's profile is used (`stretchZoom` in the result); `outputType` writes the aligned stack as uint8 or uint16, scaled from the `saturation` percentiles of the first frames, as dev's recast. Drift between parts, which dev corrects part by part, does not arise: every frame is aligned to one reference for the whole recording. The reference is the average of the first `referenceFrames` frames, then of the aligned frames. Saves the aligned stack and the shifts (frames x 2, or frames x 2 x patches²). Preset `thorough` for large or slow drift |
| `ophys.image_stats` | Frames, size, mean and maximum intensity (the computed `ophys.image_stats` columns), the average and maximum projections, and each frame's mean, minimum, maximum and standard deviation (`FrameStats`, a time series the dashboard plots, as dev's per-frame image stats) |
| `ophys.detect_rois` | ROIs as 4-connected areas of pixels whose average correlation with their 8 neighbours reaches `threshold`, of `minSize` to `maxSize` pixels, away from a `border`. ROI files are JSON: `imageSize` and `rois[{id, area, center, pixels}]`, with 0-based `[row, column]` pixels |
| `ophys.quicky` | dev's Quicky (flufinder): cells where thresholded activity recurs across bins of frames. With `useShapeDetection` (on by default, as in dev), somata are also found by their shape in the mean image, also those that are never active: a ring template (a nucleus of `innerRadius` in a ring to `outerRadius`) is correlated with the image, and each candidate's mask runs to where the image falls off beyond the ring along 48 directions from its centre. Shape ROIs come first, and an activity ROI overlapping one by more than 75 % is left out. It follows flufinder's steps, the same in both languages: each candidate's 21 x 21 patch is upsampled `upsampling` times (4, as flufinder; bicubic as imresize, with Keys' kernel and mirrored edges, in both languages), the candidates are compared on their upsampled patches, and the edge is found in its upsampled patch, sampled every upsampled pixel and pushed out by 2 of them (flufinder's 2 / us); `upsampling` 1 works at the image's own resolution; `ophys.flufinder` follows flufinder itself. Presets `soma`, `soma_virus` and `axon` are dev's Quicky presets Soma (flufinder's defaults, at most 300 ROIs), Soma (Virus) (without shape detection) and Axons (4 px boutons, the 95th percentile, no shape detection; dev's bouton masks, its RoiType, are not brought over) |
| `ophys.flufinder` | dev's flufinder (`flufinder.runAutoSegmentation`, with `RoiDiameter` `roiDiameter`), its ROIs saved as `ophys.detect_rois` saves them: in MATLAB the toolbox from NANSEN dev (add-on `nansen-dev`); in Python its pipeline written out step by step, with flufinder's constants and no toolbox (`ophys_flufinder.py`): frames binned by their maximum (5 a bin), a Gaussian of 20 px with circular edges and a moving mean of 20 bins taken out, scaled to 0..1; each bin thresholded at the 93rd percentile and cleaned with MATLAB's `strel('disk')` (its periodic-line octagons from a radius of 3); the 8-connected areas of every bin but the last (as dev's loop), the largest 1 % left out; unique ROIs where areas recur (findUniqueRoisFromComponents with its own defaults: a 12 px soma, 2 observations), overlaps merged; ring-shaped somata in the mean of the preprocessed bins (shapeDetection, its candidates' masks by `nansen.autodetect`'s port of findSomaMaskByEdgeDetection, kept by its ridge fraction); and the shape ROIs no activity ROI overlaps by more than 75 % added after them. Python computes in double precision where flufinder uses single, and decides its own way what MATLAB functions decide there (linkage clusters of areas whose centroids spread, an empty mask, dev's loops that would not end), so the two find nearly, not exactly, the same ROIs; on the quickstart's synthetic recording Python finds every cell |
| `ophys.extract_signals` | The mean of each ROI's pixels per frame (frames x ROIs, rejected ROIs left out), and of neuropil around it, outside every ROI: a ring at a fixed distance, or dev's (`neuropilMethod` `expansion`: grown by sides and diagonals in turn to `neuropilExpansionFactor` times the ROI's area, `neuropilSeparation` pixels from every ROI, at most `maxNeuropilRadius` steps out, as dev's estimateNeuropilMasks meant to stop instead of after 101). `numNeuropilSlices` above 1 splits the neuropil in slices of about equal area around the ROI (dev's splitNeuropilMasks, FISSA's: by the angle from the ROI's centroid, cut at its quantiles from the least populated of 20 bins of angle, with FISSA's turn of the angles that dev's port leaves out) and the neuropil signal is the mean of the slices' means, as dev's ΔF/F methods take them. `excludeOverlaps` leaves pixels shared by ROIs out of their signals, as dev does. `channel` 0 extracts every channel in one run, as dev's extractSignalsMultiChannel (see below) |
| `ophys.compute_dff` | ΔF/F = (F - F0) / F0, with F the signal less `neuropilFactor` times the neuropil, and F0 a percentile of F over the whole trace or a window of frames. dev's other methods are `method`s: `chen2013` adds the neuropil's baseline back to F (Chen et al. 2013), and `dffMinusNeuropil` takes the neuropil's ΔF/F from the signal's. `correctionWindow` subtracts a running percentile of ΔF/F, for slow drift |
| `ophys.roi_images` | dev's ROI classifier images and statistics (computeRoiImages, imageprops, dffprops), saved as `RoiImages` (JSON, read with `data.value`): a box of `boxSize` pixels around each ROI from its ΔF/F-weighted mean frame, the mean of its top 1% ΔF/F frames and the local correlation image, each scaled to 0..255, and the peak ΔF/F, salience and template similarity of each ROI. The viewer's ROI gallery shows these images and sorts by these statistics |
| `ophys.downsample` | Mean or maximum over bins of frames and of pixels |
| `ophys.cnmf` | Cells found by CaImAn's CNMF (CaImAn in Python, CaImAn-MATLAB in MATLAB) on the whole stack, saved as ROIs with their traces and denoised calcium; run against the real tools in CI |
| `ophys.find_plane` | The plane of a z-stack the recording's field of view is (dev's zStackPlaneFinder): its mean image against each plane, at the shift phase correlation finds, by Pearson correlation; the best plane, its shift and every plane's correlation |
| `ophys.crop` | Rows, columns and frames of a stack kept as a new stack (`TwoPhotonSeries_Cropped`), as dev's StackCropper, a chunk at a time |
| `ophys.export_nwb` | The recording, its ROIs and their signals in an NWB file, as dev's NWBExporter: a TwoPhotonSeries written a chunk at a time (frames x columns x rows), a PlaneSegmentation of pixel masks with the ROIs' ids and classification, and Fluorescence and DfOverF linked to their ROIs. pynwb in Python, matnwb in MATLAB; both are run in CI |
| `ophys.export_stack` | Frames of a stack written a chunk at a time as TIFF, dev's binary stack (`.raw` and `.ini`), `.npy`, or video (Motion JPEG AVI of 8-bit frames scaled between limits), as dev's imviewer exports. `ophys.export_tiff` is its TIFF case |
| `ophys.export_tiff` | Frames of a stack written to a TIFF file, a chunk at a time, as dev's imviewer exports a stack; the path takes `{field}` tokens of the entity |
| `ophys.deinterleave` | Frames of several channels and planes interleaved in one stack (channel fastest, then plane, as ScanImage saves them) put in a height x width x channels (x planes) x frames stack |
| `ophys.deconvolve` | Spikes and denoised calcium by OASIS, natively, towards the minimum of 1/2 |c - y|² + λ Σ s with s ≥ 0, λ = `sparsity` times the trace's noise. `order` 2, dev's default (getDeconvolutionParameters): an AR(2) model of a rise (`tauRise`, 0.18 s) and a decay (`tauDecay`, 0.55 s), whose factors at the frame rate (`frameRate`, or the entity's `frame_rate`), d = exp(-1 / (tauDecay × rate)) and r = exp(-1 / (tauRise × rate)), give the coefficients as dev's exp2ar, g1 = d + r and g2 = -d r; before the first spike the calcium decays by d, and each pool of frames is fitted with those before it fixed, greedily, as OASIS does for AR(2) (what CaImAn's OASIS class gives, with the penalty's exact weight at both ends). `order` 1: the decay only, at the exact optimum |
| `ophys.denoise` | Gaussian smoothing in space and time, renormalised at the edges (dev used DeepInterpolation, which needs a trained network) |
| `ophys.deep_interpolation` | DeepInterpolation with a trained model, as dev's Denoiser: deepinterpolation and h5py in Python; in MATLAB, as dev, DeepInterpolation-MATLAB's `deepinterp.Net` (add-on `deepinterpolation-matlab`) with the Deep Learning Toolbox, reading a Keras `.h5` model (with its Converter for TensorFlow Models) or a `.mat` file holding a network as `net`. `omittedFrames` is deepinterp's `Nomit` of 2 x `omittedFrames` + 1. Both scale the stack by one mean and standard deviation for all pixels, as DeepInterpolation's pretrained models were trained (dev's Denoiser scaled each pixel), and keep the frames too close to the ends as they were; MATLAB puts frames smaller than the network's input in its middle, as dev did for the 512 x 512 models. Both run in CI (MATLAB with an untrained network, and skipped with its reason where the Deep Learning Toolbox is missing) |
| `ophys.align_sessions` | Batch: aligns the selected entities' FOV images to the first one's and copies its ROIs, moved, to the others (dev's migrateRoisToFovs). With `maxRotation`, it also tries each angle up to that, in steps of `rotationStep`, and turns the ROIs by the angle that correlates best. With `patches` above 1, the rest is aligned piecewise, as dev's alignFovs: the image moved and turned back is cut into `patches` x `patches` patches, as the motion correction's, each finds its whole-pixel shift within `maxDeviation`, and each ROI pixel moves by the displacement field there, interpolated bilinearly between the patch centres (dev's warpRois). See *Tracking ROIs across sessions* below |
| `ophys.fov_region` | Computes the `brain_region` column: the atlas region at the FOV's position |
| `ophys.caiman_deconvolution` | CaImAn's OASIS with dev's options, when installed: `modelType` (`ar1`, `ar2` (the default), `exp2`, `autoar`: AR(2) above 15 Hz, else AR(1), estimated), `tauRise` and `tauDecay` (the AR coefficients as dev's exp2ar gives them, or estimated from each trace with `estimateTimeConstants`), `spikeSnr` (the smallest spike, in units of the trace's noise, CaImAn's GetSn) and `lambdaPr` (choose_lambda's probability; none at dev's 0.5). | `ophys.extract` | MATLAB: cells and traces by EXTRACT, when it is on the path. | `ophys.flowreg` | Non-rigid motion correction by Flow-Registration: the MATLAB toolbox when it is on the path, pyflowreg (its Python port) in Python; both run in CI |
| `ophys.suite2p` | Runs suite2p, when it is installed, and saves its cells and signals in the same variables: the suite2p package in Python, and in MATLAB, as dev, the MATLAB Suite2P (add-on `suite2p-matlab`, cortex-lab/Suite2P), through its whole pipeline as its `run_pipeline` and `add_deconvolution`: `reg2P`, `sourcery`, `extractSignalsSurroundNeuropil2`, `classifyROI` and `wrapperDECONV` (OASIS, of CaImAn-MATLAB, on each signal less `neuropilCoefficient` times its neuropil); there the options are its `imageRate`, `diameter`, `sensorTau`, `doRegistration`, `nonrigid`, `ThScaling`, `maxIterRoiDetection`, `innerNeuropil` and `minNeuropilPixels`. Without a Python that has nansen-core and suite2p it runs the MATLAB Suite2P, as dev did, and says so in its log (`dependency-missing` when that is not on the path either); a preview cannot hand it over (`method-unavailable`). Both save the aligned stack (in the stack's type) and each frame's shift (rows, columns: the shift applied, averaged over the patches) in the same variables, on the same grid: `gridSize` (or `patches` per side, dev's numRows and numCols, round(size / patches)); the whole frame is rigid. In MATLAB the options are NoRMCorre's `max_shift`, `grid_size`, `us_fac`, `max_dev`, `overlap_pre`, `iter`, `upd_template`, `init_batch` and `bin_width`. In Python they are CaImAn's `max_shifts`, `strides` (the grid), `overlaps` (cut to fit the frame) and `max_deviation_rigid`; CaImAn registers chunks of `binWidth` frames to one template rather than renewing it as it goes, so the first template is the median of the first `initialBatchSize` frames, and with `updateTemplate` `iterations` rigid passes renew it (the median of the chunks' aligned means) before the frames are aligned to it; it finds shifts to 1/10 pixel, its own, whatever `upsampling` is; frames move by Fourier shifts (rigid) or CaImAn's interpolation between patches, the edges copied from the nearest pixels (NoRMCorre's boundary `copy`). The results are close to NoRMCorre's, not the same; both run in CI against the real tools. Presets `nonrigid` and `rigid` are dev's NoRMCorre presets Nonrigid (4x4) and Rigid |
| `ophys.open_in_imviewer` | Run by hand: opens a stack in an image viewer. In MATLAB R2024b or older (imviewer uses Java figures) dev's imviewer, when it and the Widgets Toolbox are on the path. In Python napari (add-on `napari`), imviewer's Python counterpart, with the stack's frames `firstFrame`..`lastFrame` of its channel and plane as an image layer: on the main thread (a script, a notebook) there, with `napari.run()`; from the app, which runs methods on other threads, in a napari process of its own. Without napari it opens the dashboard's viewer on the entity's variable, the page `#/viewer/<entity type>/<key as JSON>/<variable>` (each part URI-encoded: the entity type's table with the viewer open over it), through the app's open-URL hook, which the app gives a method's context (`app_url`, `open_url`); run elsewhere, its result gives the page and how to open it (`opened` false) |

Stacks with channels (height x width x channels x frames) or planes (height x width x channels x planes x frames) are taken a channel and plane at a time: image statistics, ROI detection, Quicky, signal extraction, downsampling and denoising have `channel` and `plane` options (from 1). Signal extraction also takes `channel` 0, every channel in one run, as dev's extractSignalsMultiChannel: each ROI's signal is read from its own channel (its place, `channel` in the ROI file), with the neuropil reckoned among the ROIs of that channel (and plane), the columns in the file's order, as with `plane` 0; the result has a `channels` list with each channel's `rois`. An ROI without a channel is `invalid-data` there when the stack has several, and a stack of one channel is its one channel. Motion correction finds the shifts in its `channel` and aligns every channel of its `plane` by them, so a structural channel can steer the alignment of a functional one. The viewer offers the channels and planes of the stack it shows (`data.frame` gives their counts).

As dev's imviewer, the viewer shows a stack's channels together, each in its colour and added up (dev's `setChColors`): on by default for a stack with channels (**Colour** beside the channel picker), with dev's default colours (red and cyan for two channels; red, green and blue for three; red, chartreuse, cyan and violet for four; evenly spaced hues for more), a box per channel to show or hide it and a colour picker each. Each channel is scaled by its own contrast limits (automatic or set); the limits in the toolbar, the ROIs and the ROI tools are those of the channel picked. A stack with planes has imviewer's volume display: one plane, **Plane montage** (the planes side by side in a near-square grid, row by row, 10 pixels apart, each labelled with its number) or the **maximum** or **mean over planes** of the frame or projection shown. Every plane of a channel is put on one scale, from the lowest to the highest of their limits, so the planes compare. The viewer composes these from a `data.frame` per channel and plane, so both backends serve them with no further request; the time of peak projection keeps its own colours and shows one channel and plane. ROIs belong to a plane, so they are shown, listed and edited with one plane on view only. The PNG and the video export what is shown, the montage's plane labels included.

Every method that reads a stack works on a range of its frames, as dev's frame interval: `firstFrame` (from 1, by default 1) and `lastFrame` (0, the default, for the last). The stack is opened as those frames only (`_open_stack`, `ophys.internal.openStack`), so the method reads, aligns, detects and extracts from them, and its outputs have that many frames: motion correction writes `lastFrame - firstFrame + 1` frames and as many rows of shifts, signal extraction that many rows of signals. ROIs found in a range belong to the whole recording, so signals can then be extracted from any range of it. `ophys.deinterleave` counts the frames it puts together (frame k is the stack's frames (k - 1) x channels x planes + 1 to k x channels x planes); `ophys.crop` and `ophys.export_stack` had these options already and keep them. A range that is empty or not within the stack is `invalid-options`, and an image (height x width) is one frame. A preview (`methods.preview`) runs on the first frames of the range: its frames are those of the range, not of the recording, and a range outside the recording is refused there too.

`plane` 0 processes every plane of a recording with planes in one run, one plane after the other, as dev's `PlaneProcessingMode` `serial`: motion correction, image statistics, ROI detection, Quicky and signal extraction take it (ΔF/F and deconvolution work on signal columns, whatever plane they come from). Each plane is processed as it would be on its own (its own reference and shifts, its own correlation image and ROIs), and the outputs are kept in the layouts the readers already know:

| Output | With `plane` 0 |
|---|---|
| Aligned stack (motion correction) | height x width x channels x planes x frames, as the recording: `data.frame`'s `plane` picks a plane |
| Projections (image statistics' average and maximum) | height x width x 1 x planes x 1: a stack of one frame per plane, written with the trailing frame axis in both languages |
| Time series (shifts, frame statistics) | the planes' arrays joined along their last axis, plane 1's first: frames x 2 planes shifts (frames x 2 x patches² planes when piecewise rigid), frames x 4 planes statistics |
| ROIs (ROI detection, Quicky) | one ROI file, each ROI with its place, `plane` (from 1) and `channel`; numbered from 1 across the planes, plane 1's first. The viewer shows and edits those of the plane on view (`rois_at`, `rois.update`) |
| Signals (signal extraction) | a column per ROI of the options' channel, in the file's order whatever their planes, each read from its own plane, with the neuropil reckoned among the ROIs of that plane; `data.traces` with `rois`, the viewer's signal under the image and ΔF/F take the columns in that order |

The results have the figures of all planes and a `planes` list with each plane's (its `plane` and, for example, its `maxShift` and `meanShift`, its `rois`, its `mean_intensity`). Extracting every plane's signals needs ROIs with places: an ROI without one belongs to every plane, which is `invalid-data` with `plane` 0 (extract such ROIs one plane at a time). Of a stack without planes, `plane` 0 is its one plane, with the outputs of `plane` 1. The other methods take one plane at a time (`plane` 0 is `invalid-options` there).

The viewer is also where ROIs are edited, as in dev's roimanager and roiclassifier. Its tools add a round ROI where you click, take the pixels inside a line you draw (those whose centre is inside it), or detect the cell around a click with `rois.detect` in one of dev's roimanager autodetection modes, picked with keys 1-5 while the Detect tool is on and shown beside it: 1 (the default), the cell's edge in the activity-weighted mean of the frames around it; 2, a threshold of its peak activity; 3 and 4, a threshold of the average (4 in a wider box); 5, the cell's edge in the average. The tool's circle is the round ROI's radius. `i` (dev's improveRois) finds each selected ROI again around its middle in that mode, keeping its id and class. Ctrl-click selects several ROIs; `m` merges them into the first, dragging the selected ROI moves it (Alt and the arrow keys a pixel at a time), and `a`, `r`, `u` and Delete classify or remove what is selected. Every edit is a `rois.update` (classify, move, merge, remove, add, in that order). The wheel zooms, dragging pans, a double-click zooms in or back out, and the download button saves the image as PNG. The gallery button shows each ROI on the image around it, sorted by id, size or brightness, to go through with the arrow keys and classify with `a`, `r` and `u`. Find ROIs runs a segmentation method (ROI detection, Quicky, suite2p, EXTRACT, …) on the entity; when it would write into the ROI variable on screen and that has ROIs on the plane and channel on view, the method writes into `<variable>_Found` instead, and the viewer asks, as roimanager does for ROIs it loads, whether those found replace the ROIs there, are appended, or are appended where they do not overlap one of them (`rois.update` with `import`). Add ROIs from… does the same with another ROI variable of the entity. Either way only the plane and channel on view change, and Ctrl+Z puts back the ROIs there were. Neuropil (Shift+N) shows the selected ROI's neuropil over the image as `ophys.extract_signals` takes it, with its preferred preset (`rois.neuropil`, made by the same function as the extraction's). The link button shows another stack beside the one on view, as imviewer's Link to Another Viewer: another of the session's stacks (the raw recording beside the motion-corrected one) or a stack of another session, with the frame, zoom and pan in step either way until Linked is turned off.

A method that needs a package that is not installed fails with `dependency-missing`. ## Methods

A method is declared by a `nansen.method` document and implemented in either or both languages:

```json
{
  "schemaType": "nansen.method", "schemaVersion": "0.1.0",
  "id": "ophys.motion_correction", "version": "1.0.0", "title": "Correct motion",
  "entityType": "session",
  "batchMode": "serial",
  "implementations": { "python": "motion:correct", "matlab": "ophysCorrectMotion" },
  "options": {
    "type": "object",
    "properties": {
      "maxShift": { "type": "integer", "default": 20, "minimum": 0, "title": "Largest shift (px)" }
    }
  }
}
```

- `entityType` is the type the method runs on, or `*` for any type.
- `batchMode` is `serial` (the default: called once per entity) or `batch` (called once with all the entities).
- `options` is a JSON Schema. Its defaults are the method's `default` preset, and the dashboard draws its form from it. The options a method receives are the defaults, overlaid by a preset, overlaid by the options given to the run, and are validated against the schema.

The implementations take `(entity, options, context)` (or `(entities, options, context)` in batch mode) and return a value that can be written as JSON:

```python
def correct(entity, options, context):
    movie = context.project.load(entity, "movie")
    for i, frame in enumerate(movie):
        context.check_cancelled()
        context.progress(i / len(movie), "registering")
    context.project.save(entity, "motion_corrected", shifts)
    context.log(f"max shift {options['maxShift']}")
    return {"frames": len(movie)}
```

```matlab
function result = ophysCorrectMotion(entity, options, context)
    movie = context.Project.load(entity, "movie");
    ...
    context.progress(0.5, "registering"); context.checkCancelled(); context.log("max shift %d", options.maxShift);
    result = struct("frames", numel(movie));
end
```

`save` to a name the project has no data variable for makes one first, as dev's saveData does: of the entity's type, in the first data location that can be written (`access` `readwrite`), as `<name>.npy` for an array of numbers or truth values with more than one element and as `<name>.json` for anything else; it is then listed on the Data page like any other. `load` finds a file `save` wrote to a folder made since the last scan, and keeps what it read in the project's data cache (`project.data_cache`, `project.DataCache`), so methods run one after another on an entity read its files once. An entry is read again when its file changes on disk, `save` drops the entry of the file it writes, and the least recently used entries leave first once the cache holds 2 GiB. In Python, an array from the cache is read-only, so a method that changes it works on a copy (`movie.copy()`); dicts and lists are copied for each caller. MATLAB values are copied when changed anyway. `load(entity, name, cached=False)` (`Cached=false`) reads the file and keeps nothing.

The context gives the project, `log`, `progress(fraction, message)` and cancellation. Nothing else is shared: a method gets everything through its arguments.

A method fills columns it does not compute (as `ophys.read_metadata` fills `frame_rate`) with `context.project.update_values(entity, {column: value})` / `context.Project.updateValues(entity, struct(...))`: the values of columns the entity's table has are written, and their names returned (`unknown-entity` for an entity without a row). In a preview nothing is written.

Run a method now with `project.run(methodId, entities, Options=…, Preset=…)` / `project.run(method_id, entities, options=…, preset=…)`, or queue it as a task (below).

**Skipping entities where it already ran** (dev's `RedoIfCompleted` off). With `skipCompleted` (`methods.run`, `tasks.submit`, `tasks.retry`; the run dialog's *Skip entities where it already ran*), the entities the method has already completed on are left out: those the run journal (below, under pipelines) says it completed on, whose outputs are all there. The outputs are the data variables the run's options name in `output` and in any option whose name ends in `Output` (empty ones are left out); each must have a file for the entity, with no progress document beside it (a stack still being written is not done). A method with no such options is done once it has completed. `project.already_done(method_id, entities, options)` / `project.alreadyDone(methodId, entities, options)` tells, for each entity. `methods.run` answers `{results, skipped}`, the results of the entities it ran on and the keys of those it left out; a task leaves them out when it runs and lists them as `skipped`. Without `skipCompleted` (the default) a method runs on every entity it is given, as before.

A method with `entityType` `@project` is a **project tool**, as dev's project apps and scripts: it runs once on the project, as `function(project, options, context)`, from the Tools card on the overview (`tools.run`), `project.runTool(id)` or `project.run_tool(id)`. Tools are not offered for entities.

A project's own methods are documents in `methods/`, with code in `python/` and `matlab/`. Start one with `methods.create` (or `project.createMethod` / `project.create_method`, or the Methods card on the Data page): it writes the document and, per language, a file with an empty function to fill in, from `templates/`. With `computes`, it also writes a computed fragment of those columns that the method fills, and adds it to the entity type. Python code is imported again when its file changes, so an edited method runs without a restart, and no `__pycache__` is written next to it.

**Session methods of NANSEN dev** run unchanged. `methods.importLegacy` (`project.importLegacyMethods` / `project.import_legacy_methods`, or *Import dev method* on the Methods card) copies a dev session method's `.m` file (a function of dev's template, or a subclass of `nansen.session.SessionMethod`), or every one in a folder, into the project's `matlab/` folder, and writes a document with `legacySessionMethod` (`{"kind": "function"}` or `"class"`) and only a MATLAB implementation. MATLAB's `nansen.runMethod` calls dev's code with a `nansen.legacy.SessionShim` per entity, dev's session object, and with dev's default options with the run's options over them. See [legacy import](legacy-import.md#session-methods).

A fragment column can also carry `display` (`progress` for a number from 0 to 1, `badge` with `colors` per value, or `link`) and `action` (a method id run on the row when one of its cells is double-clicked in the dashboard).

**Presets** are named option sets saved in `options/<methodId>/<name>.options.nansen.json` (`nansen.options`). Use `savePreset` / `save_preset`, `presets` and `deletePreset` / `delete_preset`, or the run dialog. A module can ship presets too, listed under `presets` in `module.nansen.json`; they come after the project's own, and a project preset of the same name is used instead. Only the project's presets can be deleted. The `default` preset is always the method's schema defaults.

## Columns with choices

A string column of a fragment can list its `choices`: `entities.update` and `entities.add` refuse other values (none is always allowed) with `invalid-value`, and the dashboard edits it with a list. The CSV is read as written, so a value typed in by hand stays. `core.subject` has one: `sex` is `female`, `male` or `not detected`, as in dev.

A fragment can be taken off an entity type again with `detachFragment` / `detach_fragment` (`fragments.detach`): its columns and their values leave the table. `resetColumn` / `reset_column` (`columns.reset`) gives a column its default again, in some rows or all.

## Computed fragments

A fragment with `compute.method` is computed: its columns are filled by that method instead of typed in. The method returns a struct or dict with a value per column. `updateFragment(entityType, fragmentId)` / `update_fragment` runs it for every row, or for the given keys, and writes the table. In the dashboard, computed columns are read-only. This replaces NANSEN's table variables with update functions; dev's own table variable files are imported with `columns.import` ([below](#importing-columns-and-file-adapters)).

## File adapters

A file adapter reads a file into a value and writes a value to a file. The built-in ones are `json`, `text` and `mat` (in Python, `mat` needs SciPy: `pip install "nansen-core[mat]"`; a variable of 2 GB or more is written as MATLAB v7.3, HDF5, in both languages, which Python reads and writes with h5py), plus `npy` (NumPy arrays; read and written by MATLAB without Python, keeping NumPy's shape and indexing, and by Python with NumPy: `pip install "nansen-core[npy]"`), and `csv` and `excel` (`.xlsx`, its first sheet): a table, read as a MATLAB `table` and in Python as columns (`{name: [values]}`, numeric columns as floats with NaN where empty, as `readtable` reads them), written from a table, a struct of columns, columns or records (Excel in Python needs openpyxl: `pip install "nansen-core[excel]"`). A module adds others with a `nansen.fileAdapter` document:

```json
{ "schemaType": "nansen.fileAdapter", "schemaVersion": "0.1.0", "id": "ophys.tiff_stack", "version": "1.0.0",
  "extensions": [".tif", ".tiff"],
  "implementations": { "python": "stacks:TiffStack", "matlab": "ophys.TiffStack" } }
```

A Python implementation is a class with `read(path)` and `write(path, data)`. A MATLAB one is a subclass of `nansen.FileAdapter`. Data variables name the adapter by id. See [entities](entities.md) for how a data variable finds its file.

### Importing columns and file adapters

Code written for another project comes in with its documents, as dev's Import File Adapter and Import Table Variable.

**File adapters** (`adapters.import`, `project.importAdapter(path)` / `project.import_adapter(path)`, or *Import file adapter* on the Data page, from a file or from a folder): a `nansen.fileAdapter` document is copied into `file-adapters/`, and the code of each of its implementations into the project's `python/` and `matlab/` folders, at the place its reference names (`a.b:Class` is `a/b.py`, or the package `a/b/`; `pkg.Class` is `+pkg/Class.m`, or the class folder `+pkg/@Class/`). The code is looked for beside the document, in the `python/` or `matlab/` folder there, and in the one beside the document's folder, so a project's or a module's adapters can be imported from where they are. A folder brings every document in it and in its `file-adapters/` and `adapters/` folders; documents sharing a code file share its copy. The document must validate, its id must be new to the project, and its code must be there and hold the class with `read` and `write` (the same regular expressions in both languages); a file of other content where one would be copied is `adapter-exists`. Everything is checked before anything is copied.

**dev's own file adapters** come in the same way, unchanged: the `.m` file of a class that subclasses `nansen.dataio.FileAdapter` (with `readData`, and `writeData` when it writes), the `+<Name>` folder of dev's function-based adapter (`fileadapter.json` with `read.m` and `write.m`, or its `ReadFunction` and `WriteFunction`), or a folder of them with no document, such as a dev project's `code/+<name>/+fileadapter`. The code is copied into `matlab/` in the same packages (so `RatNav.fileadapter.SpeedTrace` keeps its name), and each gets a document `file-adapters/legacy.<name in snake case>.fileAdapter.nansen.json` with `legacyFileAdapter` (`{kind: "class"}`, or `{kind: "function", read, write}`) and its title (dev's name), description (`Description`, or the first line of the help text), `extensions` (`SUPPORTED_FILE_TYPES`, with or without the dot) and `dataType`, read from the text the same way in both languages. MATLAB reads and writes with it through `nansen.legacy.FileAdapterShim`: `Class(path).load()` and `Class(path, '-w').save(data)`, or the read and write functions, with `matlab/devcompat`'s `nansen.dataio.FileAdapter` as the class's base (dev's, less its metadata files, dialogs and `.npy` conversion). Python cannot run dev's MATLAB code in a read, so there it is `adapter-unavailable`, naming MATLAB; a method that uses it runs in MATLAB (dev's session methods do). A class may also subclass one of dev's own adapters, readers of known formats (`nansen.dataio.fileadapter.imagestack.ImageStack`, `...roi.RoiGroup`, `...timeseries.RoiSignalArray`, the modules' classes of those names, ...): it gets that adapter's data type and file types, and `legacyFileAdapter` names it (`base`) and the adapter here of each file type (`builtIn`: the ophys module's stacks and ROIs, `mat`, `npy`), with which `matlab/devcompat`'s class of dev's name reads and writes, so the subclass's own code runs on top of it unchanged ([legacy import](legacy-import.md#file-adapters)). A function, a class built on another of dev's classes (`nansen.dataio.DynamicFileAdapter`) and a script are `unsupported-file`, and named in the result's `warnings` when they are in a folder.

**Columns** (`columns.import`, `project.importColumn(entityType, path)` / `project.import_column(entity_type, path)`, or *Import a column from a file…* in the table's Columns menu) from a code file:

- dev's table variable function (`value = numFrames(sessionObject)`, which returns its default when called without input): a computed column `numFrames`, filled by a MATLAB method `num_frames` (the name in snake case, or the `id` given). dev's function is copied as it was to `matlab/num_frames_value.m`, with only its name changed, and the method gives it the entity where dev gave a session or subject object; the entity has `Key`, `values()`, `load(name)` and `locations()`, so a function that called dev's session methods (`loadData`, `getDataFilePath`, ...) needs those calls changed. A value in a cell of one (dev's text values, `{'N/A'}`) is taken out of it. The column's type is that of the default the function starts with: `true` or `false` is boolean with that default, `nan` or a number a number, `datetime` or `NaT` a datetime, anything else a string; or the `dataType` given.
- dev's table variable class (`classdef Quality < nansen.metadata.abstract.TableVariable`): a column `Quality` typed in, of the type and default of its `DEFAULT_VALUE` (as above) and with its `LIST_ALTERNATIVES` as `choices`. The class's code, which drew and edited the cell in dev's Java table, is not copied: the dashboard draws and edits the column from the fragment.
- a method of the rebuild, Python (a `.py` file with `run(entity, options, context)`) or MATLAB (a `.m` file whose function, of the file's name, takes `entity`, `options` and `context`): copied as the method of a computed column, by default one column of the file's name, of `dataType` (default `number`), or the `columns` given (as `methods.create`'s `computes`).

The fragment, of the method's id, is added to the entity type. A column the entity type has, a fragment or method of that id, another file (a script, a function of other arguments) or a file that is not `.m` or `.py` are refused, and nothing is written.

### Image stacks larger than memory, and recordings in several files

An adapter of image stacks can also have `open(paths)`, which returns a stack read a chunk of frames at a time (`nansen.stacks.Stack` in Python, `nansen.Stack` in MATLAB): height x width (x channels (x planes)) x frames, with `frames(start, stop)` reading only those frames. `cut(start, stop)` (`cut(first, last)` in MATLAB, 1-based, `last` `Inf` for the last) is a range of its frames as a stack, still read a chunk at a time, and `project.open_stack(entity, name, frames=(start, stop))` (`openStack(entity, name, [first, last])`) opens a variable as one; in a preview, the range is cut to its first frames. A range that is empty or not within the stack is `invalid-params`. Several files are one recording, joined along the frames in natural order (`part2` before `part10`), so a file pattern with `"cardinality": "many"` can match each file a microscope wrote. `npy`, `ophys.sciscan_raw`, `ophys.tiff_stack` and `ophys.scanimage_tiff` have it. `npy`, `ophys.binary_stack` and `ophys.tiff_stack` also have `create(path, shape, type)`, a writer of a new stack a chunk of frames at a time (a TIFF stack's frames in order). A ScanImage volume may begin in one file and end in the next.

- `project.open_stack(entity, name)` (`openStack` in MATLAB) gives a variable as a stack: lazily through `open` where the adapter has it, else the whole value read by `load`.
- `project.load` reads a recording in several files as one array, through `open`; with an adapter without `open`, it reads the first file.
- `project.stack_writer(entity, name, shape, dtype)` (`stackWriter(entity, name, size, className)`) writes a stack a chunk of frames at a time. An adapter's `create(path, shape, dtype)` writes each chunk to the file as it comes (`npy` does, in Fortran order so a chunk of frames is one stretch of the file); otherwise the stack is kept in memory and written with `write` when the writer closes.

### Going on where a run stopped

A long run that stops part way (a crash, Cancel, the app closed) goes on where it stopped when it runs again, as dev's ImageStackProcessor skipped the parts it had finished. A method that writes a stack a chunk at a time asks for a checkpoint of its output: `project.checkpoint(entity, name, shape, dtype, options, source, passes, method)` (`checkpoint(entity, name, size, className, options, source, Passes=…, Method=…)`; `nansen.progress.Checkpoint`, `nansen.Checkpoint`). After each chunk it saves how many frames are done and what it needs to go on from there (`checkpoint.save(pass, frames_done, **state)`, `save(pass, framesDone, state)`), in `<output file>.progress.json` beside the output file, a `nansen.progress` document. That holds the inputs the run started from (its options, the input stack's shape and type, the method's id and version) and its state: arrays kept exactly, as the base64 of their little-endian bytes in column-major order, so either language reads what the other wrote. A run with the same inputs starts from `pass_number` / `PassNumber` and `frames_done` / `FramesDone` with that `state` / `State`, and writes into the output file it had begun: `checkpoint.writer()` reopens it through the adapter's `reopen(path, shape, dtype)` (`npy` and `ophys.binary_stack` have it). The result is the one a run that never stopped gives, byte for byte. A run with other inputs starts over, as does one whose output cannot be reopened (an adapter without `reopen`, or a file that lacks frames it was said to have). `checkpoint.finish()` removes the document once the output is complete, so a run after that starts from the first frame. A method that goes through the frames more than once writes the output in its last pass; motion correction keeps each iteration's reference and the sum of the frames aligned so far (or, in the last iteration, the shifts found so far).

`ophys.motion_correction`, `ophys.denoise`, `ophys.crop` and `ophys.deinterleave` go on where they stopped. A preview keeps no progress.

The ophys methods that handle whole recordings read them this way and never whole: image statistics, motion correction (which also writes the aligned stack in chunks), ROI detection (its correlation image, in three passes), Quicky (a chunk of whole bins at a time, keeping only the bins), smoothing (each part with 3 temporal sigmas of frames on either side, so the result is the same as smoothing the whole), signal extraction and downsampling, deinterleaving, previews, and the viewer's frames and projections (`data.frame`). Only the external tools, which take an array, get the stack whole. Setting `project.stack_frame_limit` (`StackFrameLimit`) makes any read of more frames than that fail; the tests use it to show which methods read in chunks.

## Pipelines

A pipeline (`nansen.pipeline`) is an ordered list of method steps, each with an optional preset and options. Queueing it makes one chain of tasks per entity. Each step waits for the step before it, and is cancelled if that step fails or is cancelled.

An entity can also be assigned a pipeline, as in dev: the `pipeline` column of the `core.pipeline` fragment (`pipelines.assign`). Every method run that completes, in the queue or in the foreground, appends a line per entity to `runs/<entityType>.runs.jsonl`; a step is done for an entity once its method has completed on it. That gives each entity's progress (a column in the table, the steps in its drawer), and `pipelines.queueNext` queues the steps from the first not done on. Entities whose steps are queued or running already are left alone.

A pipeline can also be given to new rows by rule: its `assignWhen` holds filters, as a view's (`in`, `range`, `is`, `contains`, `empty`, `notEmpty`), and when a sync adds rows, each gets the first pipeline (in id order) whose filters it passes, on its key, the attributes read from its folder names and the columns' defaults.

A project's own pipelines are in `pipelines/` and can be made and changed in the dashboard (`pipelines.save`, `pipelines.delete`). One with the id of a module's pipeline is used instead of it.

## Tasks

A task is a method run on entities, queued in the project as `tasks/<id>.task.nansen.json`. It records entity keys, never live objects, so any process in either language can run it:

| File | Meaning |
|---|---|
| `tasks/<id>.task.nansen.json` | The task: method, entity keys, options, status (`queued`, `running`, `completed`, `failed`, `cancelled`), progress, result or error, `after` (tasks it waits for), pipeline step |
| `tasks/<id>.claim/` | Made by the worker that runs it. Making a folder is atomic, so two workers never take the same task |
| `tasks/<id>.cancel` | Asks the running worker to stop at its next `checkCancelled` |
| `tasks/<id>.log` | Log lines as they are written |

A task may name the language that must run it, and a worker only takes tasks its language can run. A Python worker runs tasks in threads, or in separate processes (`nansen app --executor process`, which uses `python -m nansen run-task`). MATLAB runs them in the foreground (`queue.runNext`, `runAll`) or on a `backgroundPool` (`queue.start`). `recover` puts back the tasks of a worker that died. `retry` (dev's Restart) queues a failed or cancelled task again; a stack it was writing when it stopped goes on where it stopped (above). A task queued with `skipCompleted` leaves out, when it runs, the entities the method already completed on, and lists them as `skipped`; `retry` keeps that unless given `skipCompleted`. A serial method's run is recorded in the run journal as soon as it is done with each entity, so a task over many entities that stops part way keeps those it finished, and its retry with `skipCompleted` runs only the rest.

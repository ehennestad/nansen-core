# Changelog

## 0.1.0 (unreleased)

The first release covers every step of the plan in [docs/architecture.md](docs/architecture.md).

**Documents and tables**

- Added the document envelope: `schemaType` + `schemaVersion` on every JSON document, per-type semantic versions, and in-memory migrations ([conventions](docs/conventions.md)).
- Added schemas for projects, fragments, tables, scans, data variables, file adapters, modules, methods, options, tasks, pipelines, the project catalog and the legacy export.
- Added the table format: CSV plus a JSON sidecar, with typed columns, distinct missing values and empty strings, canonical number and datetime forms, a key, and a revision counter for optimistic concurrency ([table format](docs/reference/table-format.md)).
- Added the project layout ([project layout](docs/reference/project-layout.md)). A project is opened from a folder, with no global state, and CI checks that the core uses no `global`, `persistent`, preferences or root appdata.

**Entities and data**

- Entities are DSM records joined with the authored tables. Table keys are checked against DSM identity, `sync` adds rows for new entities, scans are cached, and roots are chosen per environment ([entities](docs/reference/entities.md)).
- New entities get their paths from DSM's path generation (added to DSM, in both of its readers).
- Data variables find their files through DSM file patterns or file name templates, and read and write them with file adapters: `json`, `text`, `mat` and `npy`. MATLAB reads and writes `.npy` itself (C or Fortran order, either byte order), so arrays move between the languages with the shape and indexing they have in NumPy.
- `load` keeps what it read in the project's data cache, as dev's `DataCache` does: 2 GiB, least recently used out first. An entry is read again when its file's time or size changes, and `save` drops the entry of the file it writes. `load` also finds what `save` wrote to a folder made since the last scan. `load(..., cached=False)` / `Cached=false` reads without it.

- The Python app server answers only the page it served: a random token in its `index.html`, needed by `POST /api` and `GET /events`, and Host and Origin checks, so another web page in the browser cannot drive it (cross-site requests, DNS rebinding).

- Importing a dev project brings its pipelines across, with the tasks that have a method here and their rules for new sessions; tasks and option presets that cannot come across are named in the report.
- dev's two-photon data comes across: its binary stacks (`ophys.binary_stack`, read and written), its RoiGroup files with their classifications (read and written), and its ROI signals and `Default` `.mat` variables, as named variables of a file (`variableInFile`, new on data variables), which the importer maps them to.

- The Data page edits the data locations in forms, as dev's data location dialogs: name, category, access, roots, folder levels with their file patterns, naming rules, and a processed location written by methods, made from the raw one's levels. Test shows what a scan would find; the JSON stays one click away.

**Methods and tasks**

- Added modules, which provide fragments, methods, file adapters and pipelines. Added the built-in `core` module: notes, file statistics, export, backup and wait methods, an inspect pipeline, and the demo ([modules](docs/reference/modules.md)).
- Added the built-in `ophys` module, dev's two-photon workflow natively in both languages with the same results: rigid motion correction, image statistics and projections, ROI detection, signal extraction with neuropil, ΔF/F and downsampling; SciScan raw and TIFF file adapters; a tool that sets up the data variables; a preprocessing pipeline; and suite2p (Python), NoRMCorre and imviewer (MATLAB) where they are installed. A conformance case checks the results against the ground truth of a synthetic recording.
- The `ophys` module also deconvolves traces natively (OASIS, the exact optimum, checked against a general optimiser), smooths stacks, aligns sessions and copies ROIs between them, reads ScanImage TIFF files (channels, planes and multi-ROI recordings), and wraps CaImAn, EXTRACT, Flow-Registration and DeepInterpolation where they are installed.
- Modules can add pages to the dashboard (`dashboard` scripts in `module.nansen.json`, served by `app.plugins`; their files by `modules.resource`). The ophys module adds the FOV map (dev's fovmanager): cranial windows and FOVs on the dorsal cortex atlas, placed with a click and kept as columns, with each FOV's brain region computed in both languages; and the ROI review (dev's multi-session ROI classifier): each ROI across aligned sessions, accepted or rejected in all of them at once.
- Added the add-on manager (dev's AddonManager): modules declare the toolboxes and packages they use, and the Settings page lists, downloads (GitHub, into an add-ons folder on MATLAB's path), installs (pip) and removes them, in either language (`addons.list`, `addons.install`, `addons.remove`).
- Modules keep data in a project (`modules.data`, `modules.saveData`: JSON text with a revision); the FOV map keeps any number of injection sites per subject, and notes on the map, there.
- `ophys.quicky` brings over dev's Quicky (flufinder) ROI detection natively in both languages, shape detection of somata that are never active included, and `ophys.flufinder` runs flufinder itself in MATLAB. Every wrapper (suite2p, DeepInterpolation, CaImAn in Python; NoRMCorre, CaImAn-MATLAB, EXTRACT, Flow-Registration, flufinder, imviewer in MATLAB) is run against the real tool in CI.
- ROIs are curated in the dashboard's viewer: accept, reject, delete or add them (`rois.update`); signal extraction and session alignment leave rejected ROIs out.
- Motion correction can find shifts to a twentieth of a pixel (`subpixel`) and correct piecewise rigidly (`patches`), as NoRMCorre does, natively in both languages; aligning sessions can also find a rotation (`maxRotation`). A conformance case checks both languages against the ground truth: a texture moved by half pixels, quadrants that move apart, and a scene turned by 3 degrees.
- Motion correction prepares resonant-scanner recordings as dev does: flyback rows left out, the back-scanned lines' offset corrected (once or per chunk), and the aligned stack optionally written as uint8 or uint16.
- The viewer also draws polygon ROIs, grows and shrinks the selected ROI by a pixel, and undoes and redoes ROI edits (Ctrl+Z, Ctrl+Shift+Z: `rois.update` takes `restore` and `pixels`). It shows standard deviation and local correlation projections (`data.frame`, the same bytes in both languages) with a choice of colormaps, sorts the gallery by largest ΔF/F peak, and exports frames of the stack as a TIFF file (`ophys.export_tiff`, a chunk at a time; TIFF stacks can now be written a chunk at a time, `create`).
- ΔF/F by dev's other methods too (`chen2013`, `dffMinusNeuropil`), with an optional running-percentile drift correction, checked against the ground truth in both languages. Signal plots show time in seconds when the session has a `frame_rate` (`data.traces` gives `frameRate`).
- Quality control as dev's: `image_stats` saves each frame's mean, minimum, maximum and standard deviation, and time series (data type `TimeSeries`, such as these and the motion shifts, with `columnNames`) are plotted over the frames from an entity's drawer.
- Signal extraction has dev's options too: overlapping pixels left out (`excludeOverlaps`) and dev's neuropil, grown to a multiple of the ROI's area (`neuropilMethod` `expansion`), checked against ground truth in both languages.
- Video files (`ophys.video_file`, as dev's Video stack: grayscale, or colour as 3 channels), read a chunk at a time with VideoReader in MATLAB and imageio's ffmpeg in Python.
- suite2p's registered recording (`ophys.suite2p_binary`, its `data.bin`) is read a chunk at a time in both languages, with the frame size found in the bytes of its `ops.npy`, which is never unpickled.
- Tasks can run in processes (`queue.worker` setting, on the Settings page): in MATLAB on a process pool of the Parallel Computing Toolbox, as dev ran them, for methods that cannot run on backgroundPool's threads; in Python each task in a process of its own. A MATLAB test now runs a task on the background worker.
- The Data page shows what the data cache holds and empties it (`data.cache`, `data.clearCache`). Two folders that are one session (dev's duplicate sessions) are flagged in the entity's drawer, and all but one can be excluded from scans there.
- The FOV map's injection sites have a depth, volume, spread (drawn as a circle) and colour; marks are edited by clicking them and moved by dragging them, and the map is saved as PNG.
- Methods can be previewed before they run (`methods.preview`, the Preview button of the run dialog), as dev's preview mode: the method runs on the first frames of one entity's stacks, saves nothing, and shows what it returned and an image and the range of each output it would save.
- The viewer edits ROIs as dev's roimanager does: add a round one, draw one freehand, or detect the cell around a click (`rois.detect`, the same pixels in both languages); select several with Ctrl-click and merge them; move one by dragging it or with Alt and the arrow keys. It zooms with the wheel, pans by dragging, saves the image as PNG, and shows the ROIs as a gallery (dev's roiclassifier) to sort by size or brightness and classify with the keys.
- Added a viewer to the dashboard for an entity's image variables: frames one by one or played, average and maximum projections, contrast limits, and ROIs drawn over them, served by `data.frame` in both languages with the same bytes. `data.status` gives each variable's data type, and shows a file `save` wrote to a folder made since the last scan.
- Methods declare JSON Schema options and save presets, and can be implemented in MATLAB, in Python or both. Modules can ship presets; a project preset of the same name is used instead. A method with `entityType` `@project` is a project tool, run once on the project from the overview's Tools card (`tools.list`, `tools.run`). A project method can be started from templates, from the API or the Data page (`methods.create`), and Python method code is imported again when its file changes. Computed fragments are filled by a method.
- Added a task queue in the project folder, with atomic claims, cancellation, logs, recovery, retry, dependencies and pipelines. As in dev's batch processor, queued tasks can be put on hold, reordered and given new options (`tasks.hold`, `tasks.reorder`, `tasks.update`); a task is changed only while its claim is held, so no worker starts it halfway. Python runs tasks in threads or processes, and MATLAB in the foreground or on a `backgroundPool`.

**App**

- Added the app protocol, with the same API in both languages ([protocol](docs/reference/protocol.md)), and the project catalog.
- Added the dashboard: one HTML/JS app, shown by `nansen.App` in MATLAB (`uihtml`) and by `nansen app` in Python (local server with Server-Sent Events). It shows the overview, entity tables, the detail drawer, method forms with presets, pipelines, the live task queue, data and the catalog, in light and dark themes.
- Added `nansen demo` / `nansen.demo.create`: a two-photon demo project, built from the same description in both languages.
- The dashboard creates projects (optionally from an existing DSM config, with its entity types), the demo, and imports from NANSEN. A project without a dataset gets a form to set one up. Columns can be added to tables that already have rows (`fragments.create`, `fragments.attach`): NANSEN's table variables without code.
- The MATLAB app is tested end to end in CI: the dashboard loads in a `uihtml` under a virtual display, and its requests reach the API. On R2023a in CI a `uihtml` runs no page at all, so there the test checks that first and is marked incomplete.
- Added notebooks: dated notes on entities, typed as note, important, to do or question, with #tags, as dev's session and subject notebooks keep them. One `nansen.notebook` file per entity type, the `notes.list`, `notes.add` and `notes.remove` API methods, a Notes section in each entity's drawer, and a Notes page that filters by type and searches text, tags and keys.
- A fragment column can say how the dashboard draws it (`display`: a progress bar, a coloured badge per value, or a link) and what a double-click on one of its cells runs (`action`, a method run on that row), as dev's table variable renderers and double-click functions.
- Columns can be dragged to another place and sized by their edge, as in dev's table; the order and widths are kept per table and in saved views (`columnOrder`, `columnWidths`).
- Saved views of entity tables, as dev's extra metatables: a view holds a list of rows (keys) and/or filters, hidden columns and a search (`views.list`, `views.save`, `views.delete`). The table has per-column filters (a list of values, a range, yes/no, text, empty or not) shown as chips, a Views menu to switch, save, update and delete views, and the selection bar adds rows to a view or makes one. The legacy importer makes a view of each filtered table.
- Pipelines can be given to new rows by rule, as dev's pipeline assignment: a pipeline's `assignWhen` filters (as a view's) say which rows a sync adds get it; the first pipeline whose rules a row passes takes it. The pipeline editor has the rules.
- Pipeline steps can be run by hand, as dev's manual tasks: a step whose method cannot be queued stops `pipelines.queueNext`, which lists the entities waiting at it, and `pipelines.runNext` (Run now in the drawer or the Pipeline menu) runs each entity's next step in the foreground. `methods.create` can make such a method (`queueable: false`).
- Pipelines can be assigned to entities, as in dev. Progress is read from a run journal (`runs/<entityType>.runs.jsonl`, appended to whenever a method completes), shown as a progress column and in the entity's drawer, and `pipelines.queueNext` queues the steps that are left. A Pipelines page makes, edits and deletes the project's pipelines (`pipelines.save`, `pipelines.delete`), and customizes a module's.
- A file adapter can be started from the app, as dev's Create File Adapter: `adapters.create` writes its document into `file-adapters/` and a class with read and write per language from templates ("New file adapter" on the Data page).
- A computed column can be added from the app, as dev's table variables with an update function: `methods.create` with `computes` writes the method, from templates that return a value per column, and the computed fragment it fills, added to the table ("Add a computed column" in the Columns menu, then Update).
- A column of the project can be edited, as dev redefines a table variable: its title, description, unit, default and choices change from the column menu, its values stay, and the fragment goes to a new version that the tables record (`fragments.save`).
- Columns can have `choices`: the API refuses other values and the dashboard edits them with a list. A fragment can be removed from an entity type again (`fragments.detach`), and a column reset to its default (`columns.reset`), from a menu on each column header, which also sorts and hides. The new `core.subject` fragment holds date of birth, sex and species, as dev's subject table did; subject types made from a dataset get it, and the legacy importer maps dev's `DateOfBirth`, `BiologicalSex` and `Species` to it.
- Each entity's folders can be browsed in its drawer, as in dev's file viewer: a tree that opens folders in place, with sizes, and actions to show a file in the file browser or copy its path (`files.list`).
- From an entity's drawer, a data variable can be loaded into the workspace (`data.send`) and a file opened in its default app (`files.open`), as in dev's file viewer; a method's code opens in an editor from the run dialog (`methods.edit`).
- The selection can be sent to the workspace the app was opened from (`workspace.send`), as dev sends sessions to MATLAB's workspace: MATLAB's base workspace, or in Python the namespace given to `nansen.server.open_app`, which opens the dashboard from a notebook without blocking it.
- Editing can be locked in every table (as dev's table lock), so values are not changed by accident, and the dashboard has keyboard shortcuts: `/` to search, `g` then a letter or number to go to a page or table, `Esc`, and `?` for the list.
- Row and folder actions, as in dev's session context menu: copy the keys of the selected rows, remove rows from the table, show an entity's folders (or the project's) in the file browser and copy their paths (`files.resolve`, `files.reveal`, which never leave the project folder or the data roots). Ignored rows can be hidden, and a saved preset can be deleted.
- A project's title and description, and the names of its tables, are changed from the overview (`project.update`). A project whose folder was moved is found again from the Projects page (`catalog.relocate`).
- A Settings page, as dev's preferences: whether the worker starts when a project opens (kept in the catalog, `settings.get` / `settings.save`, and followed by `nansen.App`, `nansen app` and `open_app`), the theme, the editing lock and the shortcuts.
- A dataset can be described in the dashboard, as with dev's setup wizard: pick the data folder, see example names at each level, say which level holds which entity and how its names read (`sub-{subject_id}`), see what a scan would find, and keep it as the project's DSM config (`dataset.sample`, `dataset.test`, `project.setDataset` with `datasetText`).
- What a scan did not match is listed on the overview, as dev lists unmatched session folders: each entry with its location and the reason, a button to show it, and one to have scans ignore it (`scan.unmatched`, `dataset.exclude`, which adds an exclude pattern for its name to the DSM config).
- Data variables and modules are configured from the app. The Data page adds, edits and deletes data variables, choosing a location, a file pattern of the entity type's level there, and a file adapter (`dataVariables.options`, `dataVariables.save`, `dataVariables.delete`). The overview's Modules card adds and removes modules found in the project's `modules` folder or built in (`modules.list`, `modules.add`, `modules.remove`); a module the project still uses is not removed (`module-in-use`).
- A root on a removable drive is found again where the drive is mounted now, as dev does when a disk comes back under another letter: when a root's folder is missing and the DSM root has a `volumeName`, the same path inside that volume is looked for under `/Volumes`, `/media`, `/run/media`, `/mnt`, the drive with that label on Windows, and the folders in `NANSEN_VOLUME_ROOTS`.
- Data locations can be pointed somewhere else per machine (`setRoot` / `set_root`, `dataset.setRoot`, "Change path" on the Data page). Roots per environment live in the DSM config and the active environment in its `.local.json` overlay. The whole DSM config can be edited as text from the Data page (`dataset.get`, `dataset.save`): it is written as given, but only once DSM accepts it and the tables' keys still match it.
- Shared JSON files, such as a DSM config, are edited as text (`nansen.jsontext`, `nansen.internal.JsonText`), so they keep their formatting and MATLAB does not change their arrays. A `jsontext` conformance kind holds both editors to the same bytes.
- The dashboard fits narrow windows (a phone, a small `uihtml` figure): below 860 px the sidebar slides in from a menu button, and long paths and descriptions are cut with an ellipsis instead of widening the page.
- Image stacks larger than memory, and recordings kept in several files: file adapters can `open` a recording as a stack read a chunk of frames at a time, joining its files in natural order (npy, SciScan, TIFF and ScanImage, whose volumes may cross files), and `create` a writer of one chunk at a time. Image statistics, motion correction, signal extraction, downsampling and the viewer read recordings in chunks and never whole (`Project.open_stack` / `openStack`, `stack_writer` / `stackWriter`). The ophys conformance case keeps a TIFF and a ScanImage recording in two files each.
- Signals are plotted in the dashboard, as dev's signal viewer: a signal variable's Plot button in the drawer opens its traces, one panel per variable (raw, neuropil, ΔF/F, deconvolved), for one ROI or several, zoomed by dragging across; the stack viewer shows the selected ROI's trace under the image, marks the frame shown, and goes to a frame clicked on the trace (`data.traces`, in both backends, with a conformance case).
- Recordings with several channels and planes: the native ophys methods take a `channel` and `plane` (from 1) of such a stack, motion correction aligns every channel by the shifts found in one, `ophys.deinterleave` makes a channels x planes stack of interleaved frames, and the viewer has channel and plane pickers (`data.frame` gives `channels` and `planes`). The conformance case checks them on ScanImage's channels and planes and on session 1 deinterleaved as two channels, against the ground truth.
- More files read: Bruker Prairie View T-series and HDF5 stacks, and other tools' ROIs (dev's ROI `.mat` files, suite2p's `Fall.mat`, CaImAn's HDF5 results and EXTRACT's output) as the module's ROI document, in both languages. Python reads MATLAB v7.3 `.mat` files (with h5py), and MATLAB writes data of 2 GB or more as v7.3. `conformance/files/ophys` holds a file of each kind and what it must read as, checked by both languages' tests. The legacy importer keeps dev's ROI and image stack variables through these adapters.
- An edit in a table is no longer lost when the table reloads underneath it (a task finishing, a scan, a column added): the reload, or the page drawn anew, waits until the edit ends.

**Import**

- Added the importer for NANSEN dev projects: `nansen.legacy.importProject` in MATLAB, and `nansen import-legacy` in Python for an exported project ([legacy import](docs/reference/legacy-import.md)).

**Tests**

- Added conformance cases for documents, tables, projects, entities, data, legacy import and the app protocol. The MATLAB package (R2023a+) and the Python package (3.9+) both pass every case. The dashboard has browser tests.
- CI times a 5,000-session project and a 20,000-row table in both languages. CI also runs the DSM reader's own MATLAB suite against the DSM branch nansen-core uses.
